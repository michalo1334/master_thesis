\chapter{Implementation}
\label{ch:implementation}

This chapter describes the implementation of the system. The description follows the layering established in Chapter~\ref{ch:design}: the data layer, the context-graph layer, the simulation layer, the optimization layer, and the UI layer. The implementation is small enough to be discussed end-to-end, and the most important parts are illustrated with code excerpts.

\section{Context-Graph Layer}

The context-graph layer stores a typed context graph and materializes operational flows. The canonical graph holds hosts, services, and network segments as nodes, and ownership and reachability as edges. Reachability is a segment-to-segment policy that carries protocol and port-range data; no host/service flow is authored or persisted. When the simulator or the network view needs connectivity, the layer materializes one deterministic, in-memory \enquote{host to service} flow per effective host/service pair. The materializer resolves membership, ownership, policy matching, deduplication, and deterministic operational IDs; its single public entry point is \mintinline{elixir}|NetworkDefense.Graph.MaterializeReachability.materialize/1|. Source Code~\ref{src:impl:graph} shows the invariant it implements as illustrative pseudocode.

\begin{code}
	\begin{minted}{text}
for each segment-policy rule:
    for each {source host, target service} pair the rule admits:
        emit one effective operational flow
deduplicate by {source host, target service}
sort by deterministic operational id
	\end{minted}
	\caption{Illustrative pseudocode: materializing operational flows from segment policy.}
	\label{src:impl:graph}
\end{code}

Materialization is the only path from policy to concrete connectivity. It is deterministic, so the same canonical graph always produces the same flow set, which keeps simulation and optimization results reproducible.

\section{Simulation Layer}

The simulation layer is implemented as a single \mintinline{elixir}|NetworkDefense.Simulation.Simulator| module. The module exposes a function that takes the materialized operational graph, an entry point, and a number of iterations, and returns a blast-radius map. The simulator step itself is shown as implementation-independent pseudocode in Source Code~\ref{src:impl:step}. Each iteration evaluates the configured rules against the current attacker state, filters the resulting candidate actions by the per-action attempt limit, selects one candidate, and executes it with a probability drawn from the action's success probability. The iteration budget bounds the run.

\begin{code}
	\begin{minted}{text}
for each iteration up to the iteration budget:
    evaluate every configured rule against the current attacker state
    collect the candidate actions the rules emit
    drop candidates that exceed the per-action attempt limit
    if no candidates remain, end the run
    select one candidate action
    sample a uniform random number
    if the sample is at or below the action's success probability:
        execute the action and update the attacker state
    record the iteration step
	\end{minted}
	\caption{Implementation-independent pseudocode: one Monte Carlo iteration.}
	\label{src:impl:step}
\end{code}

\section{Optimization Layer}

The optimization layer applies defensive actions to the context graph: patching a vulnerability, removing a segment-policy rule, or revoking a credential. Segmentation is thus a policy removal, not a cut of individual host edges. Simulation-informed ranking and simulated annealing materialize candidate configurations and score modeled blast radius through the simulation boundary.

CVSS-priority ordering ranks vulnerabilities directly by CVSS base score. Topology-based segmentation ranks policy removals directly by the reduction in deterministically reachable hosts after flow materialization. These strategies use different selection mechanisms; no comparative evaluation is reported here.

\section{UI Layer}

The UI layer is a Phoenix LiveView application. The main page renders the current blast-radius map as a heat map, lists the top recommended defensive actions, and shows a side-by-side comparison of the current and post-defense blast-radius maps. The user can step through the recommended actions one at a time, and the visualization updates in real time as each action is applied.

The choice of LiveView is driven by the need for low-latency interaction: the user typically wants to see the effect of each candidate action immediately, and a full HTTP round-trip per action would be too slow.
