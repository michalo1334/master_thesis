\section{Design Goals}
\label{ch:design:goals}

The system is designed to satisfy a small set of explicit goals. The goals are partitioned into functional and non-functional groups.

\begin{itemize}
	\item \textbf{Functional:}
	\begin{itemize}
		\item Construct a canonical graph with segment-policy reachability and derive operational flows for simulation.
		\item Simulate attacker propagation by Monte Carlo sampling and produce a blast-radius map.
		\item Recommend defensive actions (segment-policy removals, vulnerability patches) that minimize the resulting blast radius.
	\end{itemize}
	\item \textbf{Non-functional:}
	\begin{itemize}
		\item Reproducible results: a given topology and seed must produce the same blast-radius map across runs.
		\item Reasonable scale: the pipeline should run end-to-end on a 200-host topology in under one minute on a single workstation.
		\item Implementation fits in a small number of Elixir source files, to make the system easy to study and modify~\cite{ou05mulval}.
	\end{itemize}
\end{itemize}

\section{Data Layer}
\label{ch:design:data}

The data layer consists of two inputs. The first is a \emph{network topology}: a set of network segments, hosts, and services, together with a segment-to-segment reachability policy. Each policy rule permits the source segment to initiate traffic to matching services in the target segment and carries protocol and port-range data. The second is a \emph{CVE feed}: a list of vulnerabilities, each with a CVSS base score, drawn from the National Vulnerability Database~\cite{nvd} or, in the present evaluation, a synthetic generator with the same statistical shape.

\section{Attack-Graph Layer}
\label{ch:design:graph}

The graph layer stores the topology as a typed context graph. Hosts, services, and network segments are nodes; ownership (segment contains host, host runs service) and reachability are edges. Reachability is segment policy, not a host/service flow: the stored edge connects a source to a target segment and carries protocol and port-range data. The effective \enquote{host to service} flow is a deterministic projection materialized in memory when the simulator or the network view needs it. No flow is admitted unless a policy rule supports it, and no complete static attack graph is enumerated before simulation; attack paths emerge dynamically during traversal, in the lineage of MulVAL~\cite{ou05mulval} and the multiple-prerequisite family~\cite{ingols06mpg}.

\section{Simulation Layer}
\label{ch:design:sim}

The simulation layer runs a fixed number of Monte Carlo iterations. In each iteration, a fresh attacker is dropped at the configured entry point, and propagation proceeds stochastically: at each step, the next exploit is drawn with probability proportional to its CVSS-derived weight. The output of one iteration is the set of nodes reached; the aggregate output is a \emph{blast-radius map} $\beta: V \to [0, 1]$, where $\beta(v)$ is the empirical probability that $v$ is reached across the run.

\section{Optimization Layer}
\label{ch:design:opt}

The optimization layer takes the blast-radius map and a budget $k$ of defensive actions, and returns a set of actions that minimizes the expected post-defense blast radius. The supported strategies differ only in how they select the next candidate action; all of them score candidates through the same simulation boundary:

\begin{itemize}
	\item \textbf{Policy segmentation.} Remove a segment-policy rule that admits high-blast-radius flows. Each removal is a single canonical policy change, not a cut of individual host edges; its effect on the blast radius is measured by re-materializing the flows and re-running the simulation.
	\item \textbf{Simulation-informed patching.} Rank vulnerabilities by their marginal reduction in blast radius, measured by re-simulating each candidate graph, and patch the highest-ranked ones up to the budget.
	\item \textbf{Simulated annealing.} A stochastic search over patching and segmentation actions, guided by the simulated post-defense blast radius of each candidate graph.
\end{itemize}

\section{UI Layer}
\label{ch:design:ui}

The UI layer is a Phoenix LiveView application. It shows the current blast-radius map as a heat map, allows the user to step through individual defensive actions and observe the resulting change in blast radius, and exports the final recommendation as a structured report.
